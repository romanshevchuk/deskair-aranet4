# UX review of 2026-11-14

*Last reviewed: 2026-11-14*

A critical UI/UX pass over the released app (0.1.3 plus the patch 0.1.4 work), done after the first Store users arrived. Each finding is a work item `UX-nn`. [`backlog.md`](backlog.md) lists the waves; this file holds the detail and the status of each item.

**Audience the review judged against:** Aranet4 owners who are not technical (remote workers, parents watching a bedroom, people with allergies or asthma, teachers). They want one answer ("should I open a window?") and proof that airing helped ([vision-and-scope.md](../product/vision-and-scope.md)). The main theme of the findings is **trust**: numbers, colours and words that disagree with each other.

## How to work through this list with an agent

1. **Validate.** For each item in status `validate`, the agent reproduces it (steps below), finds the cause in code, and writes one line under "Validation notes" with the file and the cause. If it does not reproduce, or the spec says otherwise, the item becomes `drop` with the reason.
2. **Decide.** Items marked `decide` need the owner. Each points to a question in [`questions.md`](questions.md) (Q54 to Q62) with options and a recommendation. Record the answer there and in `decisions.md`, then set the item to `ready`.
3. **Implement.** One item (or one tightly linked group named in the item) per branch, following `AGENTS.md`: plan first, tests for any rule or formatting change, docs and "Last reviewed" in the same change, both languages for strings.
4. **Close.** When an item is done, set it to `done` here with the branch name. When a whole wave is done, move its backlog row to `backlog-done.md`.

Statuses: `validate` (agent confirms it and finds the cause), `decide` (owner choice needed), `ready` (agreed, can be built), `doing`, `done`, `drop` (with the reason).

Type: **bug** (the app disagrees with its own spec), **change** (the spec itself changes: update the doc first), **polish** (visual or copy, no rule changes).

### How to reproduce

The original screenshots are in `artifacts/owner-screenshots/` on the owner's PC (named `live-*`, `history-*`, `settings-*`). `artifacts/` is not in git, so each item says what to look at. To see it yourself:

| Need | How |
|---|---|
| Real data with history (best) | Ask the owner for a screenshot, or run `dotnet run --project src/Deskair.App -- --sensor C3DEC8FCC7C6` on the owner's PC |
| Any screen without hardware | `dotnet run --project src/Deskair.App -- --simulated` |
| Light, dark, English, Ukrainian renders of the controls | `$env:DESKAIR_RENDER=1; dotnet test tests/Deskair.Tests --filter "FullyQualifiedName~GalleryRenderTests"` (output in `artifacts/visual/`) |

Not covered by this review (no live look was possible): the tray flyout, the toasts and the first-run screen. Item UX-45 covers that pass.
